# 启动画面与宠物模型更新设计

## 背景

首页首次打开时，启动画面根节点使用了从 `opacity: 0` 到 `opacity: 1` 的 700ms 入场动画。启动画面虽然由服务端渲染并位于首页内容之前，但根节点在首帧是透明的，因此导航、横幅和文章内容会先短暂显示，再被启动画面覆盖。

当前启动配置为完整展示 3200ms、淡出 900ms。根节点入场又占用 700ms，使用户真正看到完整启动画面的时间更短。另一个配置问题是 JavaScript 按 `fadeMs` 延迟删除节点，但 CSS 淡出时长仍使用固定回退值，二者可能不同步。

宠物清单中的狐仙模型可以完成网络加载，但模型坐标和现有 260×290 画布不适配，表现为角色很小且大部分偏出屏幕。用户同时要求移除现有白猫和黑猫，新增两个萌宠模型和两个日系人物模型。

## 目标

- 首次打开首页时，浏览器第一帧就由不透明启动画面完整遮住博客内容。
- 启动画面完整展示 3000ms，再淡出 800ms；跳过按钮继续可用。
- CSS 淡出时长和 JavaScript 清理时机使用同一份配置。
- 删除狐仙、白猫、黑猫三个宠物条目及其旧头像。
- 保留 Pio 和静香，新增两个萌宠和两个日系人物，最终共六个可切换模型。
- 新增模型使用项目内本地资源，减少远程 CDN 波动和上游路径变化带来的故障。
- 不重写现有宠物菜单和切换架构，只做兼容当前 `l2d-widget` 的模型更新和必要适配。

## 非目标

- 不修复或重新缩放狐仙模型；该模型按用户要求直接移除。
- 不制作新的 Live2D 模型，也不把宠物系统改造成 spritesheet 渲染器。
- 不改变 Pio、静香的模型来源、动作定义或默认宠物设置。
- 不重做宠物菜单布局、加载状态或气泡交互。
- 不改变启动画面仅首页显示、每个会话显示一次和可提前跳过的现有规则。

## 方案选择

### 方案一：远程 CDN 直接替换

仅修改 `manifest.json`，把四个新模型指向 jsDelivr。改动最少，但页面运行依赖第三方域名和上游文件路径，无法解决这次暴露出的资源稳定性问题。

### 方案二：兼容模型本地化（采用）

选择与当前渲染器兼容的 Cubism 2 模型，将模型配置、moc、纹理、动作、表情和物理文件放入 `public/pets/models/`，manifest 只引用站内路径。该方案工作量适中，模型切换仍沿用现有实现，并能避免运行时依赖外部 CDN。

### 方案三：原创萌宠动画

生成原创萌宠素材并扩展现有组件以支持新的动画图集。视觉独特，但会扩大到渲染器、动作协议和资源生产流程，不适合作为本次故障修复的一部分。

## 启动画面设计

### 首帧遮挡

- 移除 `.site-splash` 根节点的透明入场动画，根节点初始状态始终为 `opacity: 1`。
- 保留图片的轻微缩放和文案的内部入场动画，让启动画面仍有动态感，但这些动画不得改变根遮罩透明度。
- 为根节点保留不透明背景色。即使启动图片尚未解码，首帧也不会透出首页。
- 继续使用现有全屏固定定位和最高层级，不新增全局页面隐藏脚本。

采用 CSS 首帧遮挡而不是在 `<head>` 中提前隐藏整个页面，是因为启动节点已经服务端输出并排在正文之前。修复根透明度即可解决当前闪屏，额外的全局隐藏状态会增加无 JavaScript、会话跳过和异常恢复分支。

### 时序

- `durationMs` 改为 `3000`。
- `fadeMs` 改为 `800`。
- 启动节点通过 CSS 自定义属性接收 `fadeMs`，CSS 淡出和 JavaScript 节点移除使用同一值。
- 自动关闭总时长约为 3800ms；点击“进入小屋”时立即开始 800ms 淡出。
- `prefers-reduced-motion` 下仍尊重现有减弱动画规则，但不允许恢复根节点透明入场。

## 宠物模型设计

### 最终清单

保留：

- `pio`：少女·Pio。
- `shizuku`：少女·静香。

移除：

- `senko`：狐娘·仙狐。
- `tororo`：白猫·豆豆。
- `hijiki`：黑猫·煤球。

新增：

- `wanko`：萌宠小狗，来源 `live2d-widget-model-wanko@1.0.5`。
- `nito`：软萌团子型吉祥物，来源 `live2d-widget-model-nito@1.0.5`。
- `koharu`：日系人物小春，来源 `live2d-widget-model-koharu@1.0.5`。
- `miku`：日系人物 Miku，来源 `live2d-widget-model-miku@1.0.5`。

四个候选模型的配置地址已核验为可访问，并且配置中包含 moc、纹理和至少一组动作资源。它们与当前可正常工作的白猫、黑猫属于同一 Cubism 2 模型生态，优先保证现有 `l2d-widget@0.1.1` 的兼容性。

### 本地资源结构

每个新增模型使用独立目录：

```text
public/pets/models/<pet-id>/
  <model>.model.json
  moc/
  mtn/
  exp/          # 模型存在表情时保留
  *.physics.json
```

- 模型配置内的相对路径保持原结构，避免手工重写资源引用。
- 增加第三方来源与许可证说明，记录 npm 包名、固定版本和上游许可证。
- manifest 使用 `/pets/models/<pet-id>/<model>.model.json` 形式的站内绝对路径。
- 不保留远程 CDN 作为静默回退，避免本地缺文件时问题被掩盖；缺失资源应在测试或加载状态中明确暴露。

### 头像与文案

- 为四个新增模型生成统一尺寸、透明或干净背景的 WebP 头像，放在 `public/pets/avatars/`。
- 头像从实际模型渲染画面裁切，确保菜单缩略图与模型身份一致。
- 删除 `senko.webp`、`tororo.webp`、`hijiki.webp`。
- 为四个新模型提供简短欢迎语和与真实动作文件对应的动作按钮；不为不存在的动作配置伪交互。

### 尺寸适配

- 每个新模型在当前 260×290 画布内逐个检查。
- 只在 manifest 中设置模型级 `scale`，不为单个模型增加特殊 CSS 或坐标补丁。
- 接受标准是角色主体在左下角可辨认、不被大面积裁切、不缩小到难以互动，并且模型之间切换时视觉体量不过度跳变。
- 若某个候选无法仅靠 `scale` 达标，则在同一兼容模型库中更换候选，不扩展本次组件 API。

## 数据与交互流程

1. 组件继续请求 `/pets/manifest.json`。
2. 默认加载 Pio，保持现有默认项和初始化流程。
3. 用户打开宠物菜单时看到六个头像。
4. 悬停或触摸候选项时，现有预加载逻辑请求站内模型配置和其依赖资源。
5. 点击后继续调用 `widget.switchModel(index)`。
6. 加载成功后显示模型和真实动作；失败或超时继续使用现有恢复逻辑切回上一个模型。

## 错误处理

- 新模型的本地文件缺失时，预加载和切换流程沿用已有失败提示与恢复机制。
- manifest 必须保持有效 JSON，条目必须包含 `id`、`name`、`model` 和 `avatar`。
- 四个新增 ID 不复用已删除 ID，避免浏览器缓存和历史状态把旧模型误认为新模型。
- 不修改用户当前尚未提交的宠物可靠性逻辑；实现时在其基础上做局部合并。

## 验证

### 启动画面

- 在新的浏览器标签页首次访问首页，首帧截图中不得出现导航、横幅、文章卡片透过启动画面。
- 约 3 秒时启动画面开始淡出，约 3.8 秒时节点移除并恢复页面滚动。
- 点击跳过按钮后执行 0.8 秒淡出。
- 同一标签页会话内再次进入首页时不重复显示，保持现有规则。

### 宠物

- manifest 最终包含 Pio、静香和四个新增模型，不包含狐仙、白猫、黑猫。
- 四个新增模型的配置、moc、纹理和动作文件均能通过站内 URL 返回成功。
- 逐个切换六个模型，确认无控制台错误、无 15 秒超时、失败恢复逻辑未触发。
- 四个新增模型主体尺寸合适，头像与角色一致，动作按钮只调用真实存在的动作。
- 窄屏下菜单仍可横向滚动并选择六个头像。

### 工程检查

- 运行项目现有格式化和静态检查。
- 运行与宠物动作映射相关的测试。
- 运行 `pnpm build`。
- 使用本地浏览器完成启动首帧、自动淡出、宠物逐项切换和菜单视觉检查。

## 风险与控制

- 模型资源会增加仓库体积：仅保留运行时实际引用的文件，并记录各模型目录大小。
- 第三方模型有许可证要求：随本地资源保留来源、版本和许可证说明，不删除上游版权信息。
- 不同模型的体量和原点可能不同：先使用 manifest 的 `scale` 校准；无法达标时更换候选，不堆叠模型专用补丁。
- 工作区已有未提交修改：设计文档独立提交；后续实施只编辑本次明确涉及的行和资源目录，不覆盖其他变更。
